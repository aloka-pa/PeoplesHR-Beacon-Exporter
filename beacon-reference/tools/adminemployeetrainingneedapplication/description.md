# adminEmployeeTrainingNeedApplication

**Task:** Submitting a Training Need Application (Admin, for Any Employee)

**Tags:** T&D, Aloka, phase3

**Status:** live

## Description

Lets an Admin submit a training need application on behalf of one or more employees, company-wide (no reporting-line restriction). Resolves every named employee (employees) FIRST via the org-wide employee search. Once confirmed, identify the need (existingNeedName or newNeedName/newNeedDescription); objective, relevance to job, benefit to employee, and benefit to company are collected only if the server requires them (per-client config). On every turn the user attaches a file, call this tool on that same turn (the chat passes a file's contents only then); files are added (several allowed) if they match PeoplesHR's allowed types and size - take one off with removeAttachments, or swap with replaceAttachments. Call with confirmed unset first for a preview and the real confirmation prompt, then again with confirmed:true, before anything is validated or saved. Write tool - submits real applications, one per named employee, on success. Draft - GetSearchedEmployeeDetails not yet captured/tested for this module.

## Signature

```
adminEmployeeTrainingNeedApplication
```

## Arguments

_None._


## Advanced arguments

- `employees` (array, required) — The employee(s) to submit this training need application for, company-wide - not restricted to any reporting line. Pass each employee exactly as the Admin named them (a name or an employee number), e.g. ["Charlotte Taylor"] or ["000012"] - do NOT resolve these yourself with any other tool first. This tool runs the same employee search the real 'Select Employee' modal uses internally, and this is checked before anything else - the moment the Admin names who the need is for, call this tool with employees set (existingNeedName/newNeedName and the narrative fields all omitted) to resolve them first. If a name matches more than one employee, the tool returns status AMBIGUOUS with the matching candidates (employee number, name, date joined, active status) - ask the Admin to be more specific (e.g. use the exact employee number) and retry. If a name matches no one, the tool returns status NOT_FOUND - resolve that before asking about the need itself or any narrative field.
- `existingNeedName` (string, optional) — The name (or partial name) of an already-existing training need category to attach this application to, e.g. 'Database & Data Management' - matches case-insensitively against the category list from getAdminTrainingNeeds' existingNeedCategories. Use this when the employee's need matches a category already on file rather than describing something new. If more than one category matches, the tool returns status AMBIGUOUS with the candidates - ask which one and retry with the exact name. Either existingNeedName or newNeedName must be provided, not both. Only required once every named employee is already confirmed to exist - do not collect or pass this on the employees-only resolution call.
- `newNeedName` (string, optional) — The requested need, in the Admin's own words, when what's needed isn't already an existing category, e.g. 'Advanced Excel Macros' (the 'Requested Need' field). Either existingNeedName or newNeedName must be provided, not both. Only required once every named employee is already confirmed to exist - do not collect or pass this on the employees-only resolution call.
- `newNeedDescription` (string, optional) — A fuller description of the new requested need (the 'Requested Need Description' field on the real form). Optional even when newNeedName is given - only used alongside newNeedName, ignored for existingNeedName.
- `objective` (string, optional) — The objective of this training need. There is no goal-linking option here (confirmed live from a real Admin submission capture: IsGoalObject false, no ongoing-goals data) - always free text. Whether this is mandatory is a per-client Training & Development configuration setting (IsObjectiveMandatory) and can change between orgs - do not assume it's required and do not ask the Admin for it upfront. Call this tool with whatever is known once every named employee is confirmed to exist and the need is identified; if ValidateNeedApplication rejects the submission with 'Please specify the objective.', that confirms it's mandatory for this org - ask the Admin for it then and call this tool again with the same arguments plus objective filled in.
- `relevanceToJob` (string, optional) — How this training need relates to the employee(s)' job. Whether this is mandatory is a per-client Training & Development configuration setting (IsRelToJobMandatory) and can change between orgs - do not assume it's required and do not ask the Admin for it upfront. Call this tool with whatever is known once every named employee is confirmed to exist and the need is identified; if ValidateNeedApplication rejects the submission with 'Please specify the relevance to job.', that confirms it's mandatory for this org - ask the Admin for it then and call this tool again with the same arguments plus relevanceToJob filled in.
- `benefitToEmployee` (string, optional) — The benefit of this training need to the employee(s). Whether this is mandatory is a per-client Training & Development configuration setting (IsPotentialToYouMandatory) and can change between orgs - do not assume it's required and do not ask the Admin for it upfront. Call this tool with whatever is known once every named employee is confirmed to exist and the need is identified; if ValidateNeedApplication rejects the submission with 'Please specify the benefit to you.', that confirms it's mandatory for this org - ask the Admin for it then and call this tool again with the same arguments plus benefitToEmployee filled in.
- `benefitToCompany` (string, optional) — The benefit of this training need to the company. Whether this is mandatory is a per-client Training & Development configuration setting (IsPotentialToCompMandatory) and can change between orgs - do not assume it's required and do not ask the Admin for it upfront. Call this tool with whatever is known once every named employee is confirmed to exist and the need is identified; if ValidateNeedApplication rejects the submission with 'Please specify the benefit to the company.', that confirms it's mandatory for this org - ask the Admin for it then and call this tool again with the same arguments plus benefitToCompany filled in.
- `removeAttachments` (array, optional) — Whenever the user attaches a file, call this tool again on that same turn, with whatever arguments are already known - the chat hands this tool a file's contents only on the turn it was attached, so never just acknowledge a file, ask a question first, or call another tool instead; a file this tool never sees on its own turn has to be attached again. File names to take off this application, exactly as shown in the preview's attachments list or as attached in the chat - e.g. when the admin says 'remove images.png'. Attachments are never passed as arguments: every file the admin attaches in the chat is picked up automatically and added to the application (several files are allowed, in one message or across several). A removed file stays out on later calls even if the chat keeps listing it, so there is no need to send it again; attaching it again brings it back. A file this tool rejected for its type or size is already left out - never put it here. Never tell the admin to start a new chat to get rid of a file.
- `replaceAttachments` (boolean, optional) — Set true when the admin attaches a new file to REPLACE the earlier one(s) ('use this document instead', 'replace the attachment with this'), on the call for the message that carries the new file: the file(s) attached in that message become the only attachments and every earlier file is left out. Leave unset when they are adding another file - files are added by default. If the new file was attached in an earlier message, use removeAttachments with the old file's name instead.
- `confirmed` (boolean, optional) — Set true only after the admin has reviewed a summary of this exact application (employees, need, objective, relevance to job, benefits, attachments) and explicitly agreed to submit it. Leave unset/false on the first call - the tool returns status CONFIRMATION_REQUIRED with a preview and the server's own confirmation prompt (mirrors the real form's 'Are you sure you want to submit this training need?' dialog, shown right before Save) instead of submitting anything. Nothing is validated or saved until this is true (attached files are uploaded as soon as they are attached, as on the real form, but only become part of the application when it is saved). Call this tool again with confirmed:true and the exact same arguments once the admin agrees.
