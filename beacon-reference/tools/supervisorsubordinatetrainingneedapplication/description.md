# supervisorSubordinateTrainingNeedApplication

**Task:** Submitting a Training Need Application (Supervisor, for Subordinates)

**Tags:** T&D, Aloka, phase3

**Status:** live

## Description

Lets a Supervisor submit a training need application on behalf of one or more direct reports at once, or just list them when subordinates is omitted (answers 'who are my subordinates?' without submitting anything). Once subordinates is given, validates each against the live direct-report list FIRST. Once confirmed, identify the need; objective, relevance to job, benefit to employee, and benefit to company are collected only if the server demands them - mandatoriness is a per-client config, never assumed. On every turn the user attaches a file, call this tool on that same turn (the chat passes a file's contents only then); files are added (several allowed) if they match PeoplesHR's allowed types and size - take one off with removeAttachments, or swap with replaceAttachments. Call with confirmed unset first for a preview and the real confirmation prompt, then again with confirmed:true, before anything is validated or saved. Write tool - submits real applications, one per selected subordinate, on success.

## Signature

```
supervisorSubordinateTrainingNeedApplication
```

## Arguments

_None._


## Advanced arguments

- `subordinates` (array, optional) — One or more direct reports (each a name or employee number) to submit this training need application for, e.g. ['John Silva'] or ['000010','000011']. Matches each entry first by exact employee number, then by a case-insensitive substring match against name, against the supervisor's live subordinate list. Omit entirely (or pass an empty array) if you don't already know who this is for, or the supervisor asks 'who are my subordinates?' - the tool returns status LISTED with eligibleSubordinates and submits nothing, so this is always safe to call on its own. Once the supervisor has picked, call this tool again with subordinates set to their exact name(s) or employee number(s) - this is checked before everything else that follows, so call it with ONLY subordinates (existingNeedName/newNeedName and the narrative fields all omitted) to validate them first before ever asking about the need itself. If any entry doesn't match exactly one subordinate, the tool returns NOT_SUBORDINATE or AMBIGUOUS (whichever applies) listing every problem entry plus eligibleSubordinates - fix all of them before ever asking about the need itself or narrative fields.
- `existingNeedName` (string, optional) — The name (or partial name) of an already-existing training need category to attach this application to, e.g. 'Database & Data Management' - matches case-insensitively against the category list from getSupervisorTrainingNeeds' existingNeedCategories. Use this when the subordinate's need matches a category already on file (UAC 3.2) rather than describing something new. If more than one category matches, the tool returns status AMBIGUOUS with the candidates - ask which one and retry with the exact name. Either existingNeedName or newNeedName must be provided, not both. Only required once every named subordinate is already confirmed valid - do not collect or pass this on the subordinates-only validation call.
- `newNeedName` (string, optional) — The requested need, in the supervisor's own words, when what's needed isn't already an existing category, e.g. 'Advanced Excel Macros' (UAC 3.3 - the 'Requested Need' field). Either existingNeedName or newNeedName must be provided, not both. Only required once every named subordinate is already confirmed valid - do not collect or pass this on the subordinates-only validation call.
- `newNeedDescription` (string, optional) — A fuller description of the new requested need (the 'Requested Need Description' field on the real form). Optional even when newNeedName is given - only used alongside newNeedName, ignored for existingNeedName.
- `objective` (string, optional) — The objective of this training need. There is no goal-linking option here (confirmed live: a real multi-subordinate submission sent IsGoalObject false with no ongoing-goals data at all) - always free text, unlike the self-application tool's goalTitle alternative. Whether this is mandatory is a per-client Training & Development configuration setting (IsObjectiveMandatory) and can change between orgs - do not assume it's required and do not ask the supervisor for it upfront. Call this tool with whatever is known once every named subordinate is confirmed valid; if ValidateNeedApplication rejects the submission with 'Please specify the objective.', that confirms it's mandatory for this org - ask for it then and call this tool again with the same arguments plus objective filled in.
- `relevanceToJob` (string, optional) — How this training need relates to the subordinate(s)' job. Whether this is mandatory is a per-client Training & Development configuration setting (IsRelToJobMandatory) and can change between orgs - do not assume it's required and do not ask the supervisor for it upfront. Call this tool with whatever is known once every named subordinate is confirmed valid; if ValidateNeedApplication rejects the submission with 'Please specify the relevance to job.', that confirms it's mandatory for this org - ask for it then and call this tool again with the same arguments plus relevanceToJob filled in.
- `benefitToEmployee` (string, optional) — The benefit of this training need to the employee(s). Whether this is mandatory is a per-client Training & Development configuration setting (IsPotentialToYouMandatory) and can change between orgs - do not assume it's required and do not ask the supervisor for it upfront. Call this tool with whatever is known once every named subordinate is confirmed valid; if ValidateNeedApplication rejects the submission with 'Please specify the benefit to you.', that confirms it's mandatory for this org - ask for it then and call this tool again with the same arguments plus benefitToEmployee filled in.
- `benefitToCompany` (string, optional) — The benefit of this training need to the company. Whether this is mandatory is a per-client Training & Development configuration setting (IsPotentialToCompMandatory) and can change between orgs - do not assume it's required and do not ask the supervisor for it upfront. Call this tool with whatever is known once every named subordinate is confirmed valid; if ValidateNeedApplication rejects the submission with 'Please specify the benefit to the company.', that confirms it's mandatory for this org - ask for it then and call this tool again with the same arguments plus benefitToCompany filled in.
- `removeAttachments` (array, optional) — Whenever the user attaches a file, call this tool again on that same turn, with whatever arguments are already known - the chat hands this tool a file's contents only on the turn it was attached, so never just acknowledge a file, ask a question first, or call another tool instead; a file this tool never sees on its own turn has to be attached again. File names to take off this application, exactly as shown in the preview's attachments list or as attached in the chat - e.g. when the supervisor says 'remove images.png'. Attachments are never passed as arguments: every file the supervisor attaches in the chat is picked up automatically and added to the application (several files are allowed, in one message or across several). A removed file stays out on later calls even if the chat keeps listing it, so there is no need to send it again; attaching it again brings it back. A file this tool rejected for its type or size is already left out - never put it here. Never tell the supervisor to start a new chat to get rid of a file.
- `replaceAttachments` (boolean, optional) — Set true when the supervisor attaches a new file to REPLACE the earlier one(s) ('use this document instead', 'replace the attachment with this'), on the call for the message that carries the new file: the file(s) attached in that message become the only attachments and every earlier file is left out. Leave unset when they are adding another file - files are added by default. If the new file was attached in an earlier message, use removeAttachments with the old file's name instead.
- `confirmed` (boolean, optional) — Set true only after the supervisor has reviewed a summary of this exact application (subordinates, need, objective, relevance to job, benefits, attachments) and explicitly agreed to submit it. Leave unset/false on the first call - the tool returns status CONFIRMATION_REQUIRED with a preview and the server's own confirmation prompt (mirrors the real form's 'Are you sure you want to submit this training need?' dialog, shown right before Save) instead of submitting anything. Nothing is validated or saved until this is true (attached files are uploaded as soon as they are attached, as on the real form, but only become part of the application when it is saved). Call this tool again with confirmed:true and the exact same arguments once the supervisor agrees.
